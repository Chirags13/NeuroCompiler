Part 1–2 · ChiragOpening and the Run page (live demo)

Opening (≈ 2 min)

Run page, top of the page (mode cards). Optionally switch to Research & results → 01 Overview for the KPI cards, then come back.
Every C or C++ program is compiled with a fixed list of optimizations called -O3. It is a good compromise for typical code, but it is the same for every program. Our question was: can machine learning pick a better list of optimizations for one specific program, and make it actually run faster? Not smaller, not fewer instructions — faster, measured with a stopwatch, on programs the models have never seen.
Say the headline numbers (they are also the KPI cards in Research & results → 01 Overview).
On 33 test programs from 11 program families that were never used in training, our final system is +8.1% faster than -O3 on average (geometric mean), 9 of 33 programs are at least 5% faster, and 0 programs became slower. Because when we can't prove a speed-up, we simply keep -O3.
Point at the three mode cards.
The system has three modes. Tune is the main one: machine learning proposes candidates, and we measure them. Predict guesses without running the program, then we time its guess once to show how good it was. Compare runs every method side by side in one fair timing run.

Explain a finished result (use the saved interpreter run while the live job runs)

Background tasks → Saved runs → Tune · interpreter loop (3.83x, RL pick). Scroll to the results.
Here is a finished run on an interpreter program. -O3 takes 848 ms; the pipeline we chose takes 222 ms — 3.83× faster, with a 95% confidence interval of 3.820 to 3.838. It was confirmed in a fresh 20-round run, and the A/A control — an identical copy of -O3 timed alongside — came out at 1.000, so the measurement is clean. This pipeline came from the RL agent.
Card What changed vs -O3.
These are the changes to -O3, in plain words: tail duplication size 6 in the code generator, a cap on loop unrolling, and removing every SimplifyCFG pass. The reason it works: in an interpreter, -O3's SimplifyCFG merges the 31 separate jump points of the dispatch loop into one, so the CPU's branch predictor can't learn the pattern. Keeping them separate makes it almost 4× faster.
Card Every timed candidate vs -O3 (bar chart), then scroll to Selected sequence vs -O3 sequence.
Pink bars are RL proposals, blue are pipelines from our library; whiskers are confidence intervals. Below, the full pass list of -O3 on the left and our sequence on the right — red rows are passes we removed, green ones we added, yellow ones whose options changed. The table under it gives each candidate's median runtime in milliseconds.

Questions Chirag should be ready for

Q: Why not just always use -O3?For many programs -O3 is already best — the system then keeps -O3. But for some programs a different pipeline is much faster (here 1.2× to 3.8×), and -O3 can't know that because it applies the same steps to everyone.
Q: How long does tune take?About 1–3 minutes for these demo programs: around 24–80 compilations plus a few minutes of timing at most. Predict takes about a second (plus an optional ~20–60 s measurement).
Q: What if my program's input changes?The speed-up is measured for the input you give (args/stdin). A very different input can favour a different pipeline; the output check also uses that input. That's a stated limitation.
Q: How do you know the faster binary is correct?Every candidate's output is compared (by hash) with the -O0 build's output; any difference and it is discarded. That's strong evidence for this input, not a mathematical proof.
Q: Is the speed-up just noise?No: we time interleaved runs on a pinned CPU core, compute a 95% bootstrap confidence interval, require its lower bound above 1.01 in a fresh 20-round run, and check an A/A control (identical binary) that must be within 1%.
Part 3 · Dhanush SinghResearch & results page, sections 01–05: overview, corpus, measurement, headroom gate, wider search
Click Research & results in the top bar. Section 01 Overview: the four KPI cards and Key findings.
This page shows how the project was built and tested. The headline: tune is +8.1% on unseen programs with no regressions; a big search found +15.6% of possible speed-up; and predict, which doesn't run the program, reached only +0.6%. On the right are our pre-registered gates — checkpoints we defined before doing the work. Green passed, amber did not, and we report both.
Section 02 Corpus generation: the funnel, rejection chart, suites and families, runtime histogram, split bar.
We started from 347 open-source benchmark programs — PolyBench and the LLVM test-suite. A program is kept only if it compiles at every optimization level, gives the same output at every level, is deterministic, and runs between 0.35 and 3 seconds. 201 were rejected — most because they were too fast to time reliably. That left 146 programs in 35 families. A family is a group of programs that share code. We split by family — 91 training, 22 validation, 33 test — so the test programs come from families the models never saw, and we froze the split before any model was trained.
Section 03 Measurement: 'How a speedup is measured', selftest table, parallel-timing chart.
Everything depends on timing being trustworthy. We pin the program to one CPU core, run -O3 and the candidate interleaved in random order, and compute a paired speed-up with a bootstrap confidence interval. An A/A control — a byte-identical copy of -O3 — tells us the bias of each run. Our selftest showed bias of 0.3% or less and a confidence interval of ±0.12%. This chart shows we tested timing several programs at once: 5 cores made the noise too large, 3 cores with at most one memory-heavy program passed — so screening used 3 cores, and every number we report is re-measured on a single core.
Section 04 Headroom (Phase 3): bar chart, gate decision callout.
Before building models we asked: is there anything to gain at all? On 15 fresh programs a search found +4.00% on average, but only 4 of 15 reached +5% — our gate required 30%, we got 26.7%. So the gate was not met, and we say so. The team decided to continue with a lower target — the 'good' tier of +2 to 4% — and to re-check headroom with a wider search on new programs. We did not change the threshold to pass.
Section 05 Wider search (Phase 5): KPIs, sorted bar chart, artifact table.
That wider search, on 115 programs never searched before, found +15.6% on average (CI +10.3% to +21.7%), and 54 of 115 programs gained at least 5%. Grey bars are programs where nothing beat -O3 — 45 of them. We also checked suspicious winners: one program became 130× faster, but it executed 217× fewer instructions — the compiler had calculated the answer at compile time. We excluded it. This search data is what the models learn from.

Questions Dhanush should be ready for

Q: You missed the gate and continued anyway — isn't that cheating?We report the miss with its numbers, didn't change the threshold, and wrote the decision down before continuing. The next phase re-measured headroom on 115 new programs, and all later gates stayed strict.
Q: Why split by family and not randomly?Programs in a family share code. A random split would put near-copies in training and test, and the models would look better than they really are on new code.
Q: Why at least 0.35 seconds runtime?Shorter runs are dominated by timing noise; the selftest showed 220 ms was too noisy and 400 ms passed.
Q: What is a geometric mean, why not the normal average?Speed-ups are ratios; the geometric mean treats 2× faster and 2× slower symmetrically. The arithmetic mean would overstate gains.
Q: Why report 'excluding the largest'?One huge win (e.g. 2.8×) can lift the average a lot. Showing the result without it proves the gain isn't from one program.
Part 4 · NithinResearch & results page, sections 06–10: pass knowledge, training & validation, held-out test, IR ≠ runtime, timeline
Section 06 Pass knowledge: stacked bar chart of edits.
First we learned which single changes matter. We tried 346 single edits of -O3 on 31 programs. Each bar shows, out of 31 programs, where the edit was confirmed faster (green), confirmed slower (red), changed something insignificant, or produced an identical binary. The strongest levers are loop settings — vector width and unrolling — but every edit hurts some program. That's why there's no single better -O3: the choice must be per program.
Section 07 Training & validation: 'does ranking beat random?' chart, features, RL curve, predict panel.
The supervised model is LightGBM, a gradient-boosted decision-tree model. It predicts how much faster a pipeline will be for a program, using about 130 program features. We tested it the honest way: train on some families, test on a family it never saw, and repeat for every family. Its ranking correlation on unseen families is only about 0.11 — weak, but better than random: the best of its top-5 picks averaged 1.107× versus 1.091× for 5 random picks. The pink curve is the reinforcement-learning agent learning — but its reward is the model's prediction, not real time. And predict's models rank well on programs they trained on (0.42) but poorly on new ones (0.11) — that's why predict is weak.
Section 08 Held-out test: the method bar chart, then the summary table.
This is the final exam: 33 programs, 11 unseen families, every method re-measured on one core. Tune with RL + SL: +8.09%, CI +2.4% to +16.8%, zero programs slower. SL alone: +7.51%. Random search with the same budget of 8: +5.28% with 6 slower; the genetic algorithm +2.08%. Very important: trusting the model's single guess without timing ('ML-only top-1') gives +2.36% but makes 16 of 33 slower. So the models alone aren't reliable — the combination of model shortlist plus measurement is what works.
Scroll to the per-program table and the 'paired against tune top-8' chart.
Green cells are faster than -O3, red slower. Most programs stay at 1.000 because nothing convincing was found and -O3 was kept. The paired chart compares methods program by program; RL plus SL versus SL alone is +0.2%, which is not significant — we are honest that RL adds very little.
Section 09 IR count ≠ runtime: scatter plot.
Each dot is a measured candidate — 18,637 of them. Horizontal: how many IR instructions it has compared to -O3; vertical: how much faster it actually ran. There's no relationship — correlation -0.08. An earlier version of this project optimized instruction count and binary size and didn't get faster programs. That's why we only trust measured time.
Section 10 Timeline & decisions.
And here's the timeline, including the misses: the headroom gate not met, the surrogate gate first not met and then narrowly met, RL not beating the plain shortlist, predict advisory. Every number on this page is generated from result files by a script.

Questions Nithin should be ready for

Q: A correlation of 0.11 is tiny — why use the model at all?Because we only need it to put good candidates somewhere in the top 8 out of ~940. Measured on the test set, the model's top-8 beat 8 random candidates from the same library by +5.8% (CI excludes 0).
Q: Why LightGBM and not deep learning?Small tabular data (~130 features, tens of thousands of measurements) — gradient-boosted trees are strong there, fast, and need no GPU. A deep model would overfit with this little data.
Q: Why keep RL if it adds +0.2%?It was the team's choice to show the full RL + SL design. We state clearly that its measured effect is not significant; it never hurts because timing still decides.
Q: Isn't 33 programs too few?It's what the corpus allows while keeping whole families unseen. That's why we always show confidence intervals, which are wide (+2.4% to +16.8%).
Q: Is the +8% driven by one program?Without the largest result (durbin, 2.8×) it is still +4.9%, CI above zero, and 9 programs gain ≥ 5%.

Scroll to Tune flow (8 steps) and Predict flow.
Tune flow in eight steps: reference run, features, RL proposes, SL ranks, compile and verify, time 8 candidates against -O3, confirm the best in a fresh 20-round run, ship it or keep -O3. Predict flow: build -O3 and collect the compiler's optimization remarks, extract features, score a safe pool of 940 edits with 7 models and a harm model, apply the safety gate, and then measure the top pick once.
Card What an edit can do.
A candidate is always -O3 plus a few edits: remove a pass, repeat it, reorder, add a pass, change a pass option, change a global knob like vector width, or change code-generator flags. We call this list a genome.
Box Frozen models in the diagram, then card Technology.
The trained models are frozen: their files are listed with SHA-256 hashes, and tune refuses to run if anything changed. After every code change we run a regression check that tune's top-8 choice is identical. Technology: LLVM 18.1.8 pinned, Python with LightGBM, our own PPO in numpy, SQLite for all measurements, valgrind's cachegrind for simulated cache features, all inside WSL2; the dashboard is FastAPI with plain JavaScript and works offline.
Card Limits, stated honestly.
Limits: results are for one laptop CPU (AMD Zen 4) under WSL2; 33 test programs give wide confidence intervals; gains are for the input you give; tune needs minutes, not seconds; the Phase 3 gate was missed; RL adds very little; and predicting without running stays advisory.
Conclusion (any page, e.g. Research & results → 01 Overview).
To conclude: machine learning alone cannot reliably pick faster compiler settings — its correlation on unseen programs is about 0.1. But using it to shortlist 8 of ~940 candidates and letting careful measurement decide gives +8.1% on programs the system never saw, with no program slower than -O3. Questions Gagan should be ready for

Q: Why run on WSL2 and not native Linux?It's the machine we had. WSL2 has no hardware performance counters and can't control CPU frequency, so we compensate with interleaving, pinning, A/A controls and confidence intervals; the selftest proves timing is good enough.
Q: Would it work on another computer?The method would, but the models and pipelines were trained and measured on this CPU. On another CPU you'd re-run the selftest and ideally retrain; tune still measures on the target machine, so it never ships something slower.
Q: What is the RL agent's state, action and reward?State: program features plus edits chosen so far. Action: one of 120 macro-edits from the knowledge base. Reward: the surrogate's predicted log speed-up after 4 edits. Algorithm: PPO.
Q: What does 'frozen' mean and why?The exact model files are fixed and hash-checked, so results can be reproduced and nothing changes silently while we added predict mode and the dashboard.
Q: How is this different from existing work?Many tools tune compiler flags or learn phase ordering, often optimizing code size or instruction count. We optimize measured runtime only, with strict statistical confirmation and a guaranteed -O3 fallback, and we evaluate on unseen program families.

1. Executive summary

NeuroCompiler chooses, for each C/C++ program, a better LLVM optimization pipeline than the standard -O3. It edits the -O3 pass pipeline (removing, repeating, reordering or inserting passes, changing pass options and global knobs, and changing code-generator flags), and it judges every change only by measured runtime: a candidate must produce exactly the same output as the unoptimized program and be measurably faster than -O3, otherwise -O3 is used.

The final system (tune, RL + SL) works in four steps:

  1. A reinforcement-learning agent (PPO) proposes 24 pipelines for the new program.
  2. A supervised LightGBM model ranks them together with a library of ~913 pipelines found by search on training programs.
  3. The 8 best-ranked candidates are compiled, checked for identical output, and timed against -O3 on an isolated CPU core.
  4. The fastest is shipped only if a fresh 20-round confirmation run, with a byte-identical copy of -O3 as noise control, shows it is more than 1% faster. Otherwise -O3 ships.

Key findings

  • There is real headroom over -O3, but it is uneven. An expensive search finds +15.6% (geomean) on 115 programs it had never seen, but 45 of those programs have no measurable gain at all.
  • Models alone are weak; models plus measurement work. On unseen program families the supervised model ranks pipelines with Spearman ≈ 0.11. Trusting its single best guess without timing gives +2.4% but makes 16 of 33 programs slower. Using it to shortlist 8 candidates and then timing them gives +7.5–8.1% with 0–1 regressions.
  • Reinforcement learning adds little. PPO alone reaches +3.4%; pooled with the library (the final RL + SL) it is +0.2% over SL alone, not significant. It is kept in the final version at the user's request, and this report says so.
  • Predicting without running is hard. The compile-only predict mode reached +0.64% (CI includes 0) and missed its pre-registered success criterion, so it ships as advisory.
  • IR instruction count says nothing about runtime (Spearman -0.08 over 18,637 measured candidates). An earlier attempt that optimized IR count and size did not improve runtime; this project optimizes runtime directly.
  • One pre-registered gate was missed (Phase 3 headroom: +4.0%, 4/15 programs ≥ +5%, needed 30%). The project continued under a documented re-scope to the "good" tier (+2–4%), which the final system meets.

2. The problem and the goals

Compilers apply a fixed sequence of optimization passes (-O3) to every program. That sequence is a compromise tuned for typical code; for a specific program, a different sequence or different pass parameters can be faster. The search space is enormous (the LLVM 18 -O3 pipeline has 109 leaf passes, each with options, plus dozens of global knobs and code-generator flags), and the effect of an edit depends on the program's loops, data sizes, memory behaviour and branches.

Objective

  • Success = measurable, reproducible runtime improvement over -O3 on programs not used in training.
  • Never slower than -O3 beyond measurement noise; ideally a few percent faster.
  • Binary size (.text ≤ ~1.10× -O3, soft penalty), IR instruction count and compile time are constraints only, never objectives.
  • Deployment model: the system proposes top-k pipelines, they are compiled and briefly timed, -O3 is always among them, the fastest wins.

Success tiers (defined before the work)

Ground rules followed throughout

  • Only confirmed numbers count (30 interleaved rounds + A/A control); gates use validated (independently re-measured) numbers. Screening overstates.
  • Geomeans are always reported with and without the largest single result.
  • Thresholds and gates are never relaxed to get a pass; the data split is never redone after seeing results.
  • Measured and estimated values are labelled; every number is reproducible from scripts and result files in the repository.
  • No CPU-heavy work while a timing job runs; the machine is shared, so a "quiet guard" waits for other load to stop before timing.

3. Background: LLVM pass pipelines

LLVM's new pass manager describes an optimization level as a textual pipeline: a nested list of passes running at module, call-graph (CGSCC), function and loop level, e.g. function<eager-inv>(sroa<modify-cfg>,early-cse<>,simplifycfg<…>). opt -passes=default<O3> -print-pipeline-passes prints the exact -O3 pipeline for LLVM 18, which this project parses into a tree (109 leaf passes). Every candidate is "-O3 plus a short list of edits", called a genome.

Edit types (action spaces v1 and v2)

swapswap a pass with its neighbourreorder two function passes
insinsert a pass at a valid positionadd dfa-jump-threading after jump-threading
paramchange one option of one pass instancesimplifycfg no-switch-range-to-icmp → switch-range-to-icmp
param_allchange an option on every instance of a passevery simplifycfg: sink-common-insts off
del_alldelete every instance of a passremove every simplifycfg
knobglobal opt flag-force-vector-width=4, -unroll-max-count=2, -inline-threshold=1000
llc flagcode-generator flag-tail-dup-size=6, -align-loops=32

Action space v1 (delete / duplicate / swap / insert, six knobs, llc level) was extended to v2 (pass-option flips on one or all instances, family-wide deletes, more knobs, llc backend flags such as tail duplication, tail merging, loop alignment, cmov conversion, scheduling and jump tables, and more insertable passes such as dfa-jump-threading and gvn-sink). v2 found the fix for the evalloop interpreter: -O3's SimplifyCFG "sink common instructions" merges the interpreter's 31 indirect dispatch jumps into one, which destroys branch prediction; turning that option off restores them (up to 3.7× faster).

How a build works

clang -O3 -march=native -Xclang -disable-llvm-passes  →  start IR (with TBAA and attributes, no passes)
opt -passes=<pipeline> [knobs]                        →  optimized IR
llc -O3 [backend flags] -relocation-model=pic          →  object file
clang object -lm                                       →  binary

The start IR is taken from clang with LLVM passes disabled, not from -O0, so it keeps the metadata (TBAA, attributes) that a real -O3 build sees; otherwise the baseline would be weaker than real -O3. Multi-file programs are compiled per file and llvm-linked into one module. Binaries are cached by the hash of the optimized IR, so identical IR is never compiled or timed twice. The -O3 inliner settings are passed explicitly so that the printed -O3 pipeline reproduces default<O3>; 20 programs still differ bit-for-bit (flagged o3_mismatch), and all speedups are measured against the real default<O3> binary.

5. Phase 1 · Measurement harness

Nothing downstream can be trusted unless timing is trustworthy, so the harness came first and has its own pass/fail selftest.

How one comparison is measured

  • Pinning and isolation: benchmark processes run on one vCPU; the harness and compiles run elsewhere. ASLR is disabled for benchmark children; a 3 s busy warm-up lets frequency settle.
  • Interleaving: -O3 and the candidates run in randomized round-robin order (30 rounds plus 5 warm-up for confirmation), so slow drift affects all equally.
  • Paired statistics: speedup = median of per-round ratios; 95% confidence interval by bootstrap (4,000 resamples). A win requires the CI lower bound above 1.
  • A/A control: a byte-identical copy of the -O3 binary at a different path is timed in the same run. If it deviates from 1.0 by more than 1%, the measurement is repeated once and flagged.
  • Correctness: every candidate's output hash must equal the -O0 build's output hash (the oracle); otherwise it is discarded.
  • Quiet guard: before each timing block, the harness waits (up to 30 min) while processes from other sessions use more than 0.6 cores, and records the load.
  • Screening vs confirmation: search uses cheap screening (1 round, 2 more only if ≥ 0.98×; runs slower than 1.3× -O3 killed), then all shortlists are confirmed together in one 30-round run, the winner is minimized (useless edits removed) and validated in a fresh, independent run.

Parallel timing (multi-core A/A tests)

Timing several programs at once on different cores distorted memory-bound programs. Three workers on vCPUs 2, 6, 10 (siblings idle), with at most one memory-heavy program at a time (simulated L2 misses ≥ 20 per 1000 instructions), passed: bias ≤ 0.46%, noise about serial, known speedups within 0.2%. Five workers kept speedups unbiased but made noise 5–40× larger, so they were not used. Every reported number is in any case a serial re-measurement on one core. Code-layout randomization was tested and gave no benefit (results/layout_test_20261023-102201.json).

7. Phase 3 · Search and the headroom gate

Question: is there anything to gain over -O3 at all? Each program was searched with standard-level seeds plus random search, a genetic/evolutionary search on action space v1 (evo) and on v2 (evo2), budget 25 unique timed binaries per method, then confirmation, minimization and independent validation. The gate required, on validated numbers, ≥ 30% of programs at ≥ +5%.

11. Phase 7 · Supervised surrogate (LightGBM)

The surrogate predicts log-speedup vs -O3 for a (program, pipeline) pair. Two forms were trained: a LightGBM regressor and a LightGBM lambdarank ranker (300 trees, learning rate 0.05, 15 leaves, subsampling 0.8). Training data: every validated, confirmed and screened measurement of the training families, weighted by stage reliability, noisy programs down-weighted to 0.3, labels capped at |log 3|. Evaluation: leave-one-family-out cross-validation on the 24 development families (test families excluded automatically).

Metrics. Spearman = rank correlation between predicted and true speedups of a held-out program's candidates (1 = perfect, 0 = random). gain@k = the best true speedup among the model's top-k candidates, averaged (geomean) over programs; compared with k random candidates (rand_gain@k) and the best in the library (oracle).

12. Phase 8 · Reinforcement learning (PPO)

Design (nc/rl.py): an episode builds a pipeline for one program, one edit per step (horizon 4), choosing from 120 macro-actions taken from the knowledge base (knobs, llc flags, family-wide deletes and option flips). The state is the program's features plus the edits chosen so far; the reward is the surrogate's predicted log-speedup of the finished pipeline. Policy and value function are one-hidden-layer MLPs in numpy, trained with PPO (clip 0.2, entropy bonus 0.01, 4 epochs per update, Adam lr 3e-3, GAE λ = 0.95). Training: the 113 train+val programs, 200 iterations × 64 episodes.

The predicted return reached +0.22 log speedup, but that is the surrogate's opinion, far above what is measured. The learned policy favours -inline-threshold=1000, -unroll-max-count=2/4, llc tail-dup-size 4/6 and deleting every simplifycfg / instcombine. Its proposals collapse to about 5 distinct binaries per program.

13. The deployed system: tune (RL + SL)

bin/neurocompiler tune prog.c --args … --out prog (tune is the default mode). For a new program:

  1. Reference: build at -O0, run with the given arguments/stdin, hash the output. Every candidate must reproduce it.
  2. Features: static IR features and a quick scan of -O0…-O3/-Os runtimes (and, with --dynamic, cachegrind).
  3. RL proposes: the PPO policy generates 24 pipelines (3 × k) for this program.
  4. SL ranks: the surrogate scores the 24 RL proposals + ~913 library pipelines (winners from training programs plus random pipelines).
  5. Compile + verify: candidates are compiled in ranked order (in parallel) until 8 distinct binaries with correct output exist; binaries identical to -O3 are skipped.
  6. Selection timing: the 8 candidates and -O3 are timed interleaved, 10 rounds, on the pinned core.
  7. Confirmation: the fastest is re-measured in a fresh 20-round run with an A/A control. It ships only if the CI lower bound exceeds 1.01 and the control is clean. This removes the "winner's curse" of picking the best of 8 noisy numbers.
  8. Output: the binary (pick or -O3) and a JSON report: shipped pipeline and edits, where it came from (RL agent or library), the -O3 pipeline, every timed candidate with runtime in ms, speedup and CI, code size, and the model's top-10 ranking.

Cost: about 24–80 compiles and a few minutes of timing per program (≈ 80–190 s for the demo programs). Frozen: tune loads its model files only through results/models/tune/MANIFEST.json (SHA-256 hashes) and refuses to run if any changed; scripts/tune_regression_check.py confirms tune's top-8 order is identical before and after every code change (last run: IDENTICAL). --no-rl gives SL only.

Why the confirmation step exists: in the first Phase 9 run, ms/Applications/JM/lencod shipped at 0.979×: its pick won a 10-round selection run under parallel load and did not hold up. With the confirmation step, lencod ships -O3 (post-hoc illustration, not a re-scored result). The first demo run on "branchy" shows the same protection: the best candidate measured 1.044× in selection but 1.015× in confirmation, so -O3 shipped.

15. Predict mode

Goal: return a pipeline without running the program (compile + analysis only), in seconds. Criteria were recorded before building and not changed afterwards:

  • geomean ≥ +1.5% with 95% CI above 0 on the 33 test programs (serial re-measurement);
  • at most 2 programs measurably slower (CI upper bound < 1.0);
  • added time over a plain -O3 build ≤ 10 s (median; maximum reported).

Design

  • Separate models in results/models/predict/ with their own MANIFEST; predict never reads tune's models.
  • Features: 111 static IR features + 36 -O3 optimization-remark counts.
  • Candidate pool ("safe pool"): 164 knowledge-base single edits that never appeared in a wrong-output candidate and are harmful on ≤ 10% of the programs they change, plus 776 pairs of the top 40 (319 edits excluded for wrong output), plus proposals from its own PPO policy (pessimistic reward).
  • Ensemble: 7 LightGBM regressors (bootstrap members) predict speedup; a LightGBM classifier predicts the probability that a candidate is harmful.
  • Safety gate: ship only if the pessimistic estimate (mean − 1.28 × std across members) > 1 + margin, ≥ 80% of members agree, and harm probability ≤ τ. Thresholds (margin 0.03, τ 0.5) chosen on leave-one-family-out out-of-fold predictions of train+val only: objective = max mean log gain subject to OOF regression rate <= 2/33 (regression: label < 0.99x or harmful). Out-of-fold: 13 of 107 programs changed, 2 regressions.

Why it is hard: the effect of a pass edit depends on trip counts, data sizes, cache and branch behaviour, which the compile-time view does not contain. The ensemble ranks candidates with Spearman 0.42 on its training programs but only 0.11 on held-out families.

Measurement of the pick (added 2026-10-26, user request)

After the compile-only choice, predict now compiles its top-ranked sequence (the gated recommendation, or its best guess if the gate rejected it), checks the output against -O0, and times it against -O3 (20 interleaved rounds with an A/A control), reporting both runtimes in ms and the measured vs predicted speedup. This is reporting only: the choice, the gate, the advisory binary rule and the test-set result above are unchanged, and the added-time metric excludes it. --no-measure restores compile-only behaviour.

16. IR count is not runtime

An earlier attempt at this project reduced IR instruction count and binary size but not runtime. Across 18,637 measured candidates, the change in IR count and the change in runtime are essentially uncorrelated; candidates with > 1% fewer IR instructions were faster only 57% of the time. Fewer instructions often means less unrolling or vectorization, which is slower. This is why every decision here is made from timed runs.

20. System architecture

Offline (lanes 1–2): benchmark sources become a filtered, family-split corpus; the timing harness and the pipeline search produce labelled measurements in dataset.sqlite; features are extracted; the supervised surrogate, the RL agent, the pipeline library and predict's models are trained and frozen with hashed manifests. Online (lane 3): for a new program, the toolchain builds the reference and features, tune pools RL proposals with the library, the surrogate ranks them, the top 8 are compiled, verified and timed, and a confirmed winner or -O3 is written; predict scores its safe pool with its ensemble and gate. Interfaces (lane 4): CLI and dashboard in WSL2.

24. Limitations

  • One machine and microarchitecture (Zen 4, AVX-512) under WSL2; gains may differ elsewhere.
  • 33 test programs in 11 families: wide confidence intervals; the largest result (durbin 2.84×) moves the SL geomean from +4.3% to +7.5%.
  • The Phase 3 headroom gate was missed; the project continued under a documented re-scope.
  • Data quality marginally over the noisy-control limit (mitigated by down-weighting those labels).
  • Gate 7B: NOT MET before the Phase 4 data, narrowly met after; RL (exploratory) did not beat top-k; RL is in the final version for presentation with a measured effect of +0.2% (n.s.).
  • Predict missed its gain criterion and is advisory.
  • Output correctness is checked on one input per program (hash equality vs -O0): evidence, not proof. Gains are specific to the workload given (arguments/stdin).
  • Deployment cost: tens of compiles and minutes of timing per program for tune.
  • 20 programs are o3_mismatch (printed -O3 pipeline does not reproduce default<O3> bit for bit); their speedups are still measured against real -O3.
  • Fixed-input benchmarks allow compile-time evaluation (mandel-text); screened by instruction counts.

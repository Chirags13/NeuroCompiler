Glossary and cross-questions

Every abbreviation and uncommon term used in the NeuroCompiler presentation, dashboard and report, in plain words, followed by the hard questions you may be asked, with honest answers. Numbers are the measured results (33 held-out test programs, serial re-measurement) unless marked as predicted.

Statistics and measurement

-O3 baseline
The standard 'optimize for speed' level of clang/LLVM. Every speed-up in the project is relative to it: 1.10× means 10% faster than -O3.
Speed-up (e.g. 1.23×)
-O3 runtime ÷ our runtime. Above 1 = faster, below 1 = slower. 1.23× = 23% faster; it takes 1/1.23 = 81% of the time.
+8.09% / geomean
Geometric mean of speed-ups over programs, written as a percentage: (geomean − 1) × 100. The geometric mean is the correct average for ratios (2× faster and 2× slower cancel out).
Median
The middle value. 'Median +0.0%' on the test set means more than half the programs kept -O3 (speed-up exactly 1.0).
Excl. largest
The geomean recomputed without the single biggest result, to show the average isn't carried by one program (e.g. +8.09% → +4.92%).
CI (95% confidence interval)
The range that would contain the true value in 95% of repeated experiments. '+2.4% … +16.8%' means we are confident the true average gain is in that range. 'CI excludes 0' (or 'excludes 1×') = the effect is statistically real.
Bootstrap
A way to compute a CI by resampling the measured data thousands of times (4,000 here) and looking at the spread of the results. No assumption of a normal distribution is needed.
Paired comparison
Comparing two methods program by program (or round by round), then averaging the ratios. Removes differences between programs and between rounds, so it's more sensitive.
Interleaved runs
Running -O3 and the candidates alternately in random order (A, C, B, A, B, C …) instead of all A then all B, so slow changes (heat, background load) affect all equally.
Round / rep
One run of every binary in the comparison. Confirmation uses 20–30 rounds; screening 1–3.
Warm-up
Initial rounds that are discarded (caches, CPU frequency not settled).
A/A control / A/A test
Timing a byte-identical copy of the -O3 binary as if it were a candidate. It should measure 1.000×; any deviation is the measurement's bias/noise. Runs whose A/A deviates by more than 1% are repeated and flagged.
Noise floor
The smallest difference the measurement can reliably detect; here about 0.1–0.5% (A/A results).
Selftest
The harness's own pass/fail test: repeatability (CI < 1%), drift (< 2%), A/A bias (< 1%) and a sanity check that -O0 is clearly slower than -O3.
Drift
How much the median changes between the first and second half of a measurement; large drift = unstable machine.
Screening
A cheap, noisy timing (1 round, 2 more only for promising candidates) used to choose what to measure properly. Never reported as a result.
Confirmation
A long measurement (20–30 interleaved rounds + A/A control) of shortlisted candidates.
Validation
A fresh, independent re-measurement of the winner. Used by the gates, because picking the best confirmed value is itself biased.
Winner's curse
If you measure 8 candidates and pick the best, its number is too optimistic (you partly picked lucky noise). Fixed by re-measuring the winner in a fresh run.
Serial vs parallel timing
Serial = one program timed at a time on one core (most accurate, used for all reported numbers). Parallel = 3 programs on 3 cores at once (used only to speed up screening/search, validated by multi-core A/A tests).
Measurably slower / regression
A program whose speed-up's 95% CI upper bound is below 1.0 — slower beyond doubt.
n.s.
Not significant: the CI includes zero (or 1×), so we can't claim a difference.
Spearman correlation (ρ)
How well two rankings agree: 1 = same order, 0 = unrelated, −1 = reversed. Used to judge how well a model orders candidates.
gain@k
Best true speed-up among a model's top-k candidates, averaged (geomean) over programs. Compared with rand_gain@k (k random candidates) and the oracle.
recall@k
How often the truly best candidate is inside the model's top-k.
Oracle
The best possible choice from the library if you knew all true speed-ups (an upper bound, 1.22× here).
Tier (minimum / good / strong)
Success levels fixed in advance: minimum = no regressions or miscompiles; good = +2–4% with CI excluding 0 and ≥ 20–30% of programs ≥ +5%; strong = ≥ +5%.
Gate
A pre-registered pass/fail checkpoint between phases (headroom gate, data-quality gate, Gate 7B, RL gate, predict criteria).
Headroom
How much faster than -O3 programs can get at all (found by expensive search).
MPKI
Misses per 1,000 instructions (cache misses); ≥ 20 L2 MPKI = 'memory-heavy' program in our scheduler.
Quiet guard
Before timing, waits until other processes use less than 0.6 CPU cores (up to 30 min), because the laptop is shared.
Pinning / taskset
Forcing a process to run on one chosen CPU core (here vCPU 6) so the OS doesn't move it around.
ASLR (disabled)
Address Space Layout Randomization: the OS places memory at random addresses each run; we turn it off for benchmarks to reduce timing variation.
Layout randomization test
Checked whether randomizing code placement changes results; it gave no benefit, so it isn't used.

Compiler terms

LLVM
Open-source compiler infrastructure; clang is its C/C++ front end. We pin version 18.1.8 so every result uses the same compiler.
clang / opt / llc
clang turns C/C++ into LLVM IR (and links); opt runs optimization passes on IR; llc turns IR into machine code (the 'backend' / code generator).
IR (intermediate representation)
LLVM's internal, assembly-like language between source code and machine code. Optimizations transform IR.
IR instruction count
Number of IR instructions. Not related to runtime (ρ = −0.08); used only as a feature, never as a goal.
Pass
One optimization step (e.g. 'inline functions', 'unroll loops').
Pipeline / pass sequence
The ordered, nested list of passes the optimizer runs. -O3's pipeline in LLVM 18 has 109 leaf passes.
New pass manager
LLVM's current system for describing pipelines as text, e.g. function(sroa,early-cse,simplifycfg).
Module / CGSCC / function / loop pass
Levels a pass works at: whole program file; call-graph strongly-connected components (groups of functions that call each other, used for inlining); one function; one loop.
-O0 / -O1 / -O2 / -O3 / -Os
Standard optimization levels: none, light, standard, aggressive for speed, optimize for size. -O0's output is our correctness reference ('oracle').
Backend / code generator / llc -O level
The stage turning IR into machine instructions; it has its own optimization level and flags.
Knob
A global optimizer setting, e.g. -force-vector-width=4, -unroll-max-count=2, -inline-threshold=1000.
Inlining / inline threshold
Copying a called function's body into the caller to avoid call overhead; the threshold controls how big a function may be inlined (-O3 uses 250).
Loop unrolling
Repeating a loop's body several times per iteration to cut loop overhead; too much makes code bigger and slower.
Vectorization / vector width
Using SIMD instructions to process several values at once (e.g. 4 doubles). Vector width = how many.
SLP vectorizer
Superword-Level Parallelism: packs independent straight-line operations into vector instructions.
SIMD / AVX-512
Single Instruction Multiple Data: CPU instructions working on several values. AVX-512 is the 512-bit version on our Zen 4 CPU.
SimplifyCFG
Pass that simplifies the control-flow graph (merges blocks, removes dead branches).
sink-common-insts
SimplifyCFG option that merges identical code at the end of branches. In the interpreter (evalloop) it merged 31 dispatch jumps into one, wrecking branch prediction; turning it off gave up to 3.7×.
CFG (control-flow graph)
Graph of a function's basic blocks and the jumps between them.
Dispatch loop / computed goto
An interpreter's main loop that jumps to the code for the next instruction; separate indirect jumps per opcode predict much better.
Branch prediction
The CPU guesses which way a branch goes; wrong guesses cost ~15–20 cycles each.
Tail duplication / tail-dup-size
Backend optimization copying small block endings into their predecessors to remove jumps; the size limit is 2 by default, our picks often use 6.
Loop alignment (align-loops)
Placing loop starts at addresses that are multiples of 16/32/64 bytes, which can help instruction fetch.
cmov
Conditional move instruction: replaces a branch with a select.
Jump table
A switch statement implemented as a table of addresses.
LICM
Loop-Invariant Code Motion: moves calculations that don't change out of loops.
GVN
Global Value Numbering: removes redundant computations.
SROA
Scalar Replacement of Aggregates: splits structs/arrays into separate variables kept in registers.
instcombine
Peephole pass that combines and simplifies instructions.
Jump threading / DFA jump threading
Redirect jumps through branches whose outcome is known; the DFA variant is for state machines (switch in a loop).
TBAA
Type-Based Alias Analysis metadata: tells the optimizer that pointers of different types don't overlap. We start from clang IR with passes disabled (not -O0) so TBAA is kept and the baseline is real -O3.
-march=native
Compile for exactly this CPU (here Zen 4 with AVX-512). Same for -O3 and candidates so the comparison is fair.
.text size
Size of the machine code in the binary. Constraint only: soft cap 1.10× -O3.
llvm-link
Tool that merges several IR files into one module, so multi-file programs are optimized as a whole.
o3_mismatch
A program where our printed -O3 pass list doesn't reproduce clang's built-in -O3 bit for bit (20 programs); speed-ups are still measured against real -O3.
Compile-time evaluation
When the compiler computes a fixed-input program's answer during compilation; the 'speed-up' is then fake. Detected by instruction counts (mandel-text, 217× fewer instructions) and excluded.
Optimization remarks
Messages LLVM can emit about what it did or failed to do (e.g. 'loop not vectorized: …'). Counted as features for predict.
Miscompile / wrong output
An optimized binary that produces different output than -O0. Such candidates are always discarded.
Oracle output / output hash
The -O0 build's output, stored as a SHA-256 hash; every candidate's output hash must match it.

Machine learning and RL

ML / SL
Machine learning / supervised learning: learning from examples with known answers (here: measured speed-ups).
Surrogate model
A model that predicts the result of an expensive experiment (timing) so fewer experiments are needed. Ours predicts a pipeline's speed-up for a program.
LightGBM
A fast library for gradient-boosted decision trees (Microsoft). Strong on tabular data.
Gradient boosting
Builds many small decision trees one after another, each correcting the previous ones' errors (here 300 trees, 15 leaves each).
Regressor vs ranker (lambdarank)
A regressor predicts a number (the speed-up); a ranker learns only the order of candidates. LambdaRank is a ranking objective. Tune uses the regressor.
Features
Numbers describing a program/candidate: static IR statistics (111), scan runtimes (9), simulated cache behaviour (11 + 2), compiler remarks (36), and the candidate's edits (~98).
Static vs dynamic features
Static = from the code without running it. Dynamic = from running it (runtimes, cachegrind simulation).
cachegrind (simulated)
Valgrind tool that simulates caches and branch prediction while running a program. Labelled 'simulated' because WSL2 has no hardware counters; uses -march=x86-64-v3 builds because valgrind can't run AVX-512.
Label / label cap / weight
Label = the true answer (measured log speed-up). Capped at |log 3| so extreme values don't dominate; programs with noisy A/A controls get weight 0.3.
Log speed-up
ln(speed-up); symmetric for faster/slower, used for training and averaging.
Train / validation / test split
Train = learn; validation = choose settings; test = final exam, used once. Split by family, frozen before modelling.
Family
Programs sharing code (e.g. all PolyBench linear-algebra kernels). Kept together so test families are truly unseen.
Leave-one-family-out cross-validation (LOFO CV)
Train on all development families except one, test on that one, repeat for each family. Honest estimate for unseen code.
Out-of-fold (OOF) predictions
Predictions for each program made by a model that did not train on it (from cross-validation); used to choose predict's thresholds.
Overfitting
A model memorizing its training programs: predict's models rank training programs at 0.42 but unseen ones at 0.11.
Ensemble (7 members)
Several models trained on resampled data; their spread shows uncertainty.
Pessimistic estimate
Mean minus 1.28 × standard deviation across ensemble members (≈ the 10th percentile). Predict ships only if this is above 1.03×.
Agreement
Share of ensemble members predicting a gain; predict needs ≥ 80%.
Harm classifier / p_harm / τ (tau)
A model estimating the probability that a candidate makes the program slower. Predict needs p_harm ≤ τ = 0.5.
Margin
Minimum predicted gain (0.03 = 3% for predict; 0.01 = 1% for tune's confirmation).
Safe pool
Predict's candidates: 164 single edits that never produced wrong output and are harmful on ≤ 10% of programs, plus 776 pairs.
Pipeline library
~913 pipelines that won on training programs plus random pipelines: tune's candidate pool.
Gate 7B
Checkpoint: does the surrogate rank unseen families better than random? First NOT MET, then narrowly met after more data (Spearman +0.111, gain@5 1.107× vs 1.091×).
RL (reinforcement learning)
Learning by trial and reward instead of labelled answers.
PPO
Proximal Policy Optimization: a stable RL algorithm that limits how much the policy changes per update (clip 0.2).
Policy / value function (actor-critic)
Policy (actor) chooses actions; value function (critic) estimates expected reward to reduce variance. Both are small neural networks (one hidden layer) written in numpy.
Episode / horizon
One attempt at building a pipeline; horizon = number of edits per episode (4).
Action / macro-action
One edit chosen by the agent, out of 120 macro-edits from the knowledge base (knobs, llc flags, family-wide deletes, option flips).
Reward
The surrogate's predicted log speed-up of the finished pipeline (not a real measurement, which would be far too slow).
GAE (λ = 0.95)
Generalized Advantage Estimation: a way to estimate how much better an action was than expected.
Entropy bonus
Small reward for keeping the policy random enough to keep exploring (0.01).
Adam
A standard optimizer for neural-network training (learning rate 3e-3).
RL + SL
Final design: RL proposes 24 pipelines, pooled with the library, SL ranks all, timing decides. Measured gain from RL over SL: +0.2% (not significant).
ML-only top-1
Shipping the model's single best guess without timing: +2.36% but 16 of 33 programs slower — shows timing is essential.
Random search@8 / random top-8 / GA@8
Baselines with the same budget of 8 timed binaries: 8 random genomes; 8 random pipelines from the library; a genetic algorithm (6 + 18 evaluations).
GA / evolutionary search (evo, evo2)
Search that mutates and recombines the best pipelines over generations. evo uses action space v1, evo2 v2.

Project-specific terms

NeuroCompiler
This project: ML + RL guided selection of LLVM pass pipelines, judged only by measured runtime vs -O3.
Tune
Main mode: propose (RL + SL) → compile + verify → time 8 vs -O3 → confirm → ship pick or -O3. Minutes per program.
Predict
Mode that chooses without running the program (≈ 1 s), then times its top pick once for reporting. Advisory: writes -O3 unless --apply.
Compare
Mode that times -O3, -O2, -Os, predict, tune, random@8 and GA@8 in one interleaved run with an A/A control.
Advisory
Predict missed its pre-registered gain criterion, so by default it writes the -O3 binary and only reports its recommendation.
--apply / --no-measure / --no-rl / --dynamic
Predict: write the recommended binary / skip the timing of the pick. Tune: SL only / add cachegrind features.
Genome
A candidate described as -O3 plus a list of edits (del, dup, swap, ins, param, param_all, del_all, knob, llc flag, backend level, or a whole 'raw' standard pipeline).
Level seed / raw pipeline
A whole standard pipeline (e.g. default<O2> or default<O0>) used instead of -O3's, possibly with llc -O3.
Action space v1 / v2
Edit sets for search: v1 = delete/duplicate/swap/insert + 6 knobs + llc level; v2 adds pass-option flips, delete-all, more knobs, llc flags and more passes.
Knowledge base (passkb)
Phase 4 table of 346 single edits tried on 31 programs: confirmed faster/slower, no-op counts.
Minimization
Removing edits from a winner that don't contribute, so the final pipeline is as small as possible.
Phase 1–9
1 harness, 2 corpus, 3 search + headroom gate, 4 knowledge base, 5 data collection, 6 features, 7 surrogate, 8 deployment + RL, 9 frozen-test evaluation.
Corpus / prescan / scan
The set of benchmark programs; prescan = fast parallel filter (build, run, output); scan = pinned timing at every level.
PolyBench / LLVM test-suite / SingleSource / MultiSource
Benchmark collections: PolyBench (numerical kernels), test-suite SingleSource (one-file programs, C and C++) and MultiSource (multi-file programs and applications).
TSVC
A family of 33 vectorization test programs; too large for the test budget, so it went to training.
evalloop
A small interpreter benchmark where -O3's SimplifyCFG hurts; pathological case, always report results with and without it.
durbin
polybench/durbin, the largest test result (2.8×); the reason we report 'excluding largest'.
lencod
ms/Applications/JM/lencod (video encoder): the one regression in the first SL test run (0.979×), which led to the confirmation step.
mandel-text
Program excluded as a compile-time-evaluation artifact.
MANIFEST / frozen models
File listing each model file's SHA-256 hash; tune and predict refuse to load changed files.
Tune regression check
Script confirming tune's top-8 choice is IDENTICAL before and after code changes.
machine_id
Label stored with every measurement (wsl2-ryzen9-270 for 8 vCPUs, -v14 for 14 vCPUs); results from different machines are never mixed.
timing_cpu / vCPU / SMT sibling
vCPU = virtual CPU seen by WSL2. timing_cpu = 6. SMT sibling = the other hardware thread on the same physical core (vCPU 7), kept idle when timing in parallel.
helper CPUs
Cores used for compiling and output checks while timing cores stay quiet.
k
Number of candidates timed per program (8).
WSL2
Windows Subsystem for Linux 2: a real Linux kernel in a lightweight VM on Windows. No CPU frequency control or hardware counters.
FastAPI / uvicorn / SSE
Python web framework / web server running the dashboard / Server-Sent Events: how the live terminal output is streamed to the browser.
SQLite (dataset.sqlite)
File database holding every candidate, build and measurement.
Re-scope
The recorded user decision after the missed Phase 3 gate: continue with the 'good' tier target; later gates stay strict.

Cross-questions and answers

Q: What exactly is new in this project?Optimizing measured runtime only (not size or IR count), with a strict statistical protocol (interleaving, A/A controls, bootstrap CIs, fresh confirmation), a guaranteed -O3 fallback, and evaluation on unseen program families; plus an honest comparison of ML-only, ML + timing, RL, random search and GA at equal budget.
Q: Is +8% meaningful? -O3 is already highly tuned.Yes, it is measured on unseen programs with CI +2.4% to +16.8%, and +4.9% even without the largest result. Most programs keep -O3 (median 0%); the gains come from the programs where -O3's one-size-fits-all choice is wrong.
Q: Why does the median show 0%?On 21 of 33 test programs nothing convincing beat -O3, so -O3 was kept (speed-up exactly 1.0). That's by design: we only change what we can prove is faster.
Q: How can a compiler setting give 3.8×?In the interpreter, -O3 merges 31 indirect jumps into one, so the CPU's branch predictor can't learn the pattern; keeping them separate removes most mispredictions. It's a known kind of problem (dispatch loops) and the extreme case.
Q: Couldn't the gains be noise or luck in code placement?Each comparison includes an A/A control (identical binary) that measures ~1.000; a code-layout randomization test showed no effect; and winners are re-measured in a fresh run. Reproduced results differ by < 0.5% (e.g. 1.663× vs 1.656×).
Q: Why not optimize for code size or instruction count — it's faster to evaluate?We measured 18,637 candidates: IR count and runtime are uncorrelated (ρ = −0.08). An earlier attempt that optimized them didn't speed programs up.
Q: Your Phase 3 gate failed. Why should we trust the rest?We report the miss, didn't relax the threshold, documented the decision before continuing, and the later out-of-sample search on 115 new programs found +15.6%. The final test was run once on frozen data.
Q: Isn't changing the plan after a failed gate 'p-hacking'?We lowered the success target (to the more modest 'good' tier) rather than redefining the test, wrote it down before continuing, and kept all later gates strict. The test set was frozen before modelling and evaluated once.
Q: Is the model overfitting?The tune surrogate is evaluated on unseen families (Spearman 0.11) — weak but not overfit to the point of failure, and the final test is on unseen families. Predict's models do overfit (0.42 train vs 0.11 unseen), which is why predict is advisory.
Q: Why only 33 test programs?We need whole families unseen and enough programs for training; 33 programs / 11 families was the budget. We show CIs to make the uncertainty visible.
Q: Why is RL in the final version if it doesn't help?Team decision to present the full RL + SL design. Its measured effect is +0.2% (not significant), and RL alone is 4.2% worse than the SL shortlist. It never hurts, because timing still decides.
Q: Why did RL not help?Its reward is the surrogate's prediction, which is weak on unseen programs; the agent learned to please the model, and its proposals collapse to about 5 distinct binaries per program.
Q: Why not train RL with real timing as reward?Each reward would need compiling and timing a program for seconds; PPO needs hundreds of thousands of episodes. That would take months on one laptop.
Q: Why not use a GNN or a large language model on the code?With ~146 programs, a deep model would overfit badly. LightGBM on hand-built features is the right size for this data. A GNN was an option for later, not needed for the result.
Q: Why WSL2 — isn't timing unreliable there?WSL2 has more noise and no frequency control. We measured that noise (selftest, A/A tests) and designed around it; every claimed gain is well above the noise floor.
Q: Does it work on other CPUs?Not tested. Pipelines and models were learned on AMD Zen 4. Because tune measures on the target machine and falls back to -O3, it won't ship a slowdown, but gains may differ.
Q: What if the input changes?The pipeline is chosen for the input given. A different input can change which pipeline is best; the correctness check also uses that input.
Q: How do you guarantee correctness?Output hash equality with the -O0 build on the given input, for every candidate. Strong evidence, not proof; undefined behaviour in a program could still differ on other inputs.
Q: How long does it take and is that practical?Tune: about 1–3 minutes for the demo programs (tens of compiles plus timing). Worth it for programs run many times (benchmarks, scientific codes, production services); predict is ~1 s but advisory.
Q: Why is predict so much worse than tune?Without running, the model can't see trip counts, data sizes, cache and branch behaviour, which decide whether an edit helps. Its ranking drops from 0.42 on training programs to 0.11 on new ones.
Q: What does the safety gate do in predict, concretely?Ships only if the pessimistic estimate (mean − 1.28 std of 7 models) > 1.03×, ≥ 80% of models agree, and harm probability ≤ 0.5. Without the gate, predict was −0.69% with 8 slower programs and 2 wrong-output picks.
Q: Why geometric mean and not arithmetic?For ratios the geometric mean is symmetric (2× and 0.5× cancel); the arithmetic mean overweights big wins.
Q: What does 'CI excludes 0' mean?The 95% confidence interval of the average gain is entirely above zero, so the gain is statistically real.
Q: Why 20 rounds for confirmation and 30 for research data?Research confirmations use the full 30 rounds. Tune's 20-round confirmation keeps deployment fast while giving CIs well under ±1% on the demo programs. Be open about the history: the confirmation step was added AFTER the first test run showed the lencod regression (0.979×); the test result was not re-scored with it. The later RL + SL test runs used it and had 0 regressions.
Q: Why the 1.01 margin?To ship only gains clearly above the noise floor (A/A within ~0.5%). In a demo it rejected a branchy-code candidate that confirmed at 1.015×; re-running lencod with it ships -O3 (a post-hoc illustration, not a re-scored test result).
Q: What is the A/A control for, in one line?It times an identical copy of -O3; if the measurement says that copy is faster or slower, the measurement is biased and is repeated.
Q: Who decided what, and is it documented?Every decision and result is recorded with its result file in CLAUDE.md and the final report; all numbers are reproducible with scripts in the repository.
Q: What was the hardest problem?Making timing trustworthy on a shared laptop in WSL2 (pinning, interleaving, A/A, quiet guard, multi-core tests), and resisting the temptation to trust model predictions without measuring.
Q: What would you do next?Test on other CPUs, more programs/families, input-robust selection (several inputs), and features that capture runtime behaviour without full runs (e.g. short profiling).
Q: How is this related to existing tools (autotuners, MLGO, CompilerGym)?Autotuners search flags by running programs; ML approaches like MLGO learn individual heuristics (e.g. inlining) mainly for size; CompilerGym provides RL environments often rewarding IR count. Our system combines a learned shortlist with strict runtime measurement and an -O3 guarantee, evaluated on unseen families.
If you don't know: say "I don't know that exact number; the result files are in the repository and the report lists them" — never guess a number. Always separate measured (we timed it) from predicted (a model's guess).
